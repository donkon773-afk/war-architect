# ADR: Синхронизация LLM с исполнительным ИИ NeroAI

**Статус:** Proposed — архитектура подготовлена, новый протокол ещё не подключён к игре.
**Дата:** 14.10.2026.
**Область:** Operations/frontlineCampaign, затем отдельный адаптер Warlords. Реализация не должна менять исходный объект группы, штатные задачи Warlords или BIS_WL_funds.

## Контекст

Требуется сократить галлюцинации, расход токенов и задержки командования, сохранив возможность стратегического, тактического и точечного управления. В коде кампании уже есть самостоятельные механизмы: campaignDoctrine, campaignBuy, campaignVehicleOrder, campaignRide/campaignLift, campaignAirTask, campaignService, campaignAirDefense. В bridge/server.js и protocol.js уже проверяются действия и приказы игрока. Это реальные исходники; полноценная синхронизация нового командования с кампанией ещё не реализована. Последние новые игровые системы прошли проверки исходников/пакетов, но требуют движковой приёмки.

## Решение

LLM выбирает цель, приоритет, исполнителя и готовый навык. Проверяемый диспетчер принимает структурированное действие; исполнительный ИИ сам строит маршрут, занимается посадкой, наведением, снабжением и восстановлением после препятствий. Ошибки разрешаются сначала локально, затем эскалируются LLM с конкретным reason_code. LLM не генерирует SQF и не определяет физическую успешность действий.

Три уровня управления используют один протокол и одну фактическую картину мира:

| Уровень | Что решает | Что исполняет игра |
|---|---|---|
| Стратегия | Направление наступления, резерв, распределение снабжения, состав сил, приоритетные цели | Закупки, развёртывание, очереди задач и ограничения ресурсов |
| Тактика | Выбор навыка отряда, машина перевозки, высадка, прикрытие, цели артиллерии/авиации | Последовательность навыка, движение, посадка, бой и обслуживание |
| Точечное вмешательство | Задача конкретному AI-бойцу/машине/экипажу на ограниченный срок | Движковые команды конкретному владельцу объекта с сохранением общей задачи |

Ни одна модель не участвует в покадровом наведении, перехвате, посадке, реакции на ракету или открытии парашюта игроком. Эти реакции должны работать при полностью отключённой LLM. Точечное вмешательство — краткая подзадача, а не передача модели джойстика.

## Контур синхронизации

1. Arma публикует минимальный снимок и события: сущности, видимые контакты, ресурсы, доступные навыки, текущие задачи и владельцы.
2. Node нормализует события, хранит состояние с версией, ограничивает очереди и передаёт модели только факты её стороны.
3. LLM возвращает ограниченный пакет действий с идентификаторами из снимка.
4. Node проверяет структуру и устаревание; сервер Arma повторно проверяет текущие ресурсы, контакт, полномочия и ограничения задачи.
5. Сервер выдаёт право управления нужному исполнителю. Владелец группы/машины подтверждает начало.
6. Исполнитель сообщает этапы, блокировку или завершение. Только фактическое движковое подтверждение считается результатом.

ACK различает RECEIVED, VALIDATED, STARTED. Получение сообщения мостом не означает, что боты выполнили приказ. При отсутствии STARTED по истечении срока команда переводится в EXPIRED/FAILED, а не SUCCESS.

Файловый транспорт сохраняет раздельные out/in и атомарные записи через имеющуюся очередь. Новый адаптер кампании получает отдельный канал/namespace и версию протокола; он не подменяет старые Warlords-файлы. Вмешательство распространяется только через явный набор разрешённых диспетчеров; ответы модели не компилируются и не исполняются как код.

## Реестр навыков

Каждый навык описывает: id/version, тип исполнителя, параметры, предусловия, этапы, права на ресурсы, стоимость, причины отказа, правила отмены, локальное восстановление и фактический критерий завершения. Доступные навыки вычисляет игра; модель не может объявить недоступный навык доступным.

| Навык, предлагаемый ID | Существующая основа | Пример проверяемого результата |
|---|---|---|
| CAPTURE_ADJACENT | campaignGraph, campaignOrder, campaignLoop | Реальная смена владельца допустимого соседнего сектора |
| DEFEND_SECTOR | campaignDefense, campaignVehicleOrder | Отряд достиг назначенной позиции и перешёл к обороне |
| TRANSPORT_SQUAD | campaignRide, campaignLift | Все назначенные пассажиры физически высажены в допустимой зоне |
| PURCHASE_DEPLOY | campaignBuy, campaignDoctrine | Оплата один раз, экипаж назначен, техника приступила к задаче |
| SUPPLY_ROUTE / REARM_ASSET | campaignLogistics, campaignConvoy, campaignService | Доставка/боезапас подтверждены, ресурс склада списан |
| CAS / INTERCEPT / ESCORT | campaignAirTask | Самолёт получил роль/цель и приступил к соответствующему этапу |
| STANDOFF_STRIKE | campaignAirTask, campaignStandoff, campaignSpecialLoop | Допустимые цели, сопровождающий и реальный запуск боеприпаса |
| AIR_DEFENSE_POSTURE | campaignAirDefense | Фактическое состояние излучения и доступного целеуказания |
| RECRUIT / REINFORCE | campaignRecruit, campaignReinforce | Созданы допустимые бойцы/отряд и сохранена исходная группа |

Приказ TRANSPORT_SQUAD не превращается в список «купить вертолёт — лететь — сесть — посадить»: эти этапы уже принадлежат исполнителю. Если нет безопасной площадки, исполнитель пробует ограниченное число альтернатив, затем сообщает NO_SAFE_LZ. Модель выбирает другое решение только после этого.

Критерий завершения боевой задачи не обязан означать уничтожение врага: CAS может вернуть FIRED/NO_VALID_TARGET/REARM_REQUIRED, а результат поражения публикуется отдельным наблюдаемым событием. Это предотвращает ложные отчёты о попадании.

## Управление конкретным бойцом и машиной

Предлагаемые точечные действия: MOVE_TO_ANCHOR, TAKE_COVER, OBSERVE_CONTACT, ENGAGE_CONTACT, BOARD_ASSIGNED_SEAT, DISEMBARK_ASSIGNED, CHANGE_POSITION, SET_RADAR_POSTURE, SET_AIR_ROLE, SELECT_TARGET_PRIORITY, CANCEL_SUBTASK. Это план расширения белого списка, а не уже реализованные команды.

Опасные действия проходят дополнительные предусловия. Для переносного ЗРК требуются живой известный контакт, подходящий боеприпас и достижимый режим стрельбы; для водителя MOVE_TO_ANCHOR преобразуется в задачу машине, а не отдельный приказ пешему бойцу. Пилот получает ограниченную роль/направление, а не прямые команды управления рулём. Для станции РЛС LLM задаёт режим AUTO/EMIT/SILENT, но исполнитель проверяет ограничения сети и безопасность. Модель не увеличивает дальность ПВО, запас ракет, средства стороны или точность оружия.

Объект группы сохраняется. Краткая подзадача бойца резервирует его внутри исходной группы; после выполнения он возвращается к текущей совместимой задаче. Выделение постоянного экипажа/нового отряда — отдельная операция с явной стоимостью и изменением организации.

## Приоритеты и право управления

Ресурсы управления: group.task, unit.task, vehicle.motion, vehicle.weapon:t, sensor.posture, cargo.seat. Для каждой задачи сервер хранит controller_id, task_id, epoch, lease_until. Вложенная подзадача требует согласованного права родителя и резервирует только нужные ресурсы. Права выдаются атомарно сервером; конфликтующие команды отклоняются BUSY_RESOURCE. Закупки и складские ресурсы резервируются отдельно от управления движением.

Прямой приказ игрока отменяет конфликтующее право LLM. Для игрока, ручного UAV/Zeus и High Command нельзя автоматически захватывать управление. Для AI-бойцов в группе игрока требуется явное делегирование выбранных ресурсов/юнитов; оно не даёт права управлять самим игроком. Физические пределы движка и локальные защитные проверки продолжают действовать. Защитные реакции автоматического ИИ могут временно приостановить его задачу, но не забирают управление у игрока.

При передаче объекта другому владельцу увеличивается ownership_epoch, прежний исполнитель останавливает свои команды, новый подтверждает текущую задачу. Запоздалые команды предыдущей эпохи отклоняются. По завершении подзадачи восстанавливаются только свойства, которые изменил данный контроллер, и только если нет нового владельца/приказа. Нельзя восстановлением старой задачи отменить более свежий приказ игрока.

Состояния: PROPOSED → VALIDATED → RESERVED → STARTED → RUNNING → SUCCEEDED/FAILED/CANCELLED/EXPIRED. PAUSED допустим с причиной и ограниченным сроком. Идентичное повторное сообщение возвращает прежний результат, не создаёт повторную покупку или посадку. На этапе отказа все ещё не потреблённые резервы освобождаются.

## Факты и защита от галлюцинаций

Стабильные ID задаёт сервер: группы, бойцы, техника, сектора, контакты, точки высадки. Контакты содержат observed_at, last_known_position, source, confidence и доступность действия. Модель получает сведения только своей стороны; отсутствие свежего контакта не заменяется истинными координатами противника из allUnits.

Действия используют известные ID/анкеры вместо придуманных объектов и координат. Для выбора новой позиции игра заранее генерирует несколько допустимых анкеров с характеристиками укрытия/дороги/опасности. Произвольные координаты возможны только в отдельно разрешённом режиме с проверкой карты и территории. Приказ игрока с конкретными координатами сохраняет их смысл, а не меняется по вкусу модели.

action_id/session_id/epoch, task_revision, snapshot_seq, deadline_at и необходимые предусловия защищают от повторов и устаревших решений. Смена session_id обнуляет неприменимые очереди. Ответ на старый снимок можно принять только после повторной проверки затронутых фактов; изменение несвязанных объектов не должно отклонять весь пакет. Зависимости между действиями задаются явно, исполнение не «наполовину успешно» без отчёта по каждому действию.

## Пример ответа, проект контракта

```json
{
  "protocol": "nero-command/1",
  "session_id": "test-session",
  "snapshot_seq": 418,
  "actions": [
    {
      "action_id": "a-92",
      "executor_id": "group-west-3",
      "expected_epoch": 7,
      "expected_task_revision": 12,
      "scope": "GROUP",
      "skill": "TRANSPORT_SQUAD",
      "arguments": {"destination_id": "sector-8", "transport_id": "vehicle-21", "landing_anchor_id": "lz-8b"},
      "expires_after_ms": 8000,
      "lease_seconds": 120
    }
  ]
}
```

expires_after_ms отсчитывается мостом от времени выдачи запроса, а не от момента, который придумала модель. lease_seconds начинает действовать после STARTED и ограничивается сервером по навыку. Модель не назначает себе priority/player_authority. JSON здесь иллюстрирует архитектуру; production schema и диспетчер ещё предстоит реализовать.

## Задержки, контекст и промпт

Для управляемого сценарием ИИ следует определить единый adapter-owned decision point вместо независимых приказов LLM и прежнего супервизора. Запускать LLM каждые несколько секунд без изменения ситуации нельзя. Стратегия вызывается при изменениях фронта/ресурсов или периодически; тактика — по значимым событиям; точечное вмешательство — только по запросу или исключению. Исходные ориентиры для прототипа: стратегический интервал 30–90 с, тактический 5–15 с, допустимость ответа на срочное исключение 2–5 с. Это не измеренные характеристики текущих моделей. Если модель не укладывается в срок, реакцию выполняет локальный ИИ, ответ модели отбрасывается или используется только для ещё актуального продолжения.

Одновременно один активный inference на backend/GPU, если измерения не подтвердили пользу параллельности. Микро- и тактические запросы получают очередь с приоритетом/сроком; стратегия объединяет изменения и не вытесняет срочное управление. По одному актуальному запросу на контур задачи, дедупликация одинаковых событий, ограничение размера очереди и backpressure. Устаревшие запросы снимаются до начала генерации. Прерывание генерации учитывает возможности backend, но ответ с истёкшим сроком никогда не исполняется.

Промпт строится из версионированного общего контракта, кратких карточек реально доступных навыков, текущей задачи и небольшого снимка. Не отправлять полный каталог техники, все исходники и всю историю боя каждый раз. Повторно использовать стабильный префикс и краткие подтверждённые итоги. Экономия KV/prefix cache зависит от backend и должна измеряться, а не обещаться. Ответ — только действия/короткий reason_code, без chain-of-thought. Общий потолок ответа 4096 токенов сохраняется; размер нормального пакета ограничивается числом действий и длиной полей.

Для начала достаточно одного backend и двух логических очередей; существующий стратегический/тактический DualLLM можно подключить через общий адаптер. Новая архитектура не требует покупки второй модели. Более быстрая модель для точечных решений — опция после измерений, не обязательная зависимость.

## Варианты и последствия

| Вариант | Преимущества | Ограничения |
|---|---|---|
| LLM генерирует подробные команды движения/боя | Максимальная свобода | Большие задержки, конфликт задач, трудно проверить безопасность и успешность |
| LLM только стратег | Простота, низкая частота запросов | Нет требуемого точечного вмешательства |
| Выбранный: иерархия целей, навыков и временных прав | Все три уровня, меньше контекста, проверяемость и автономность | Требуются реестр навыков, арбитр задач, события и движковые подтверждения |

Промпт становится короче, но исполнитель и синхронизация сложнее. Старые супервизоры нельзя просто оставить параллельно с новым диспетчером: каждый затронутый supervisor должен уважать права/epoch и не возвращать бота к старой задаче. Warlords и Operations разделяют контракт, но используют разные адаптеры целей/денег/групп.

## Этапы реализации и приёмка

1. Shadow mode: публиковать задачи/контакты/события и предложения модели, не отдавая приказов. Сравнить с фактическими действиями; измерить задержки, токены и отказы.
2. Версионированный контракт, валидатор, журнал состояний, дедупликация и серверный арбитр. Тесты: повторная покупка, мёртвый/чужой actor, утраченный контакт, потеря снабжения, старый snapshot/session/epoch.
3. Управление на уровне группы: DEFEND_SECTOR, TRANSPORT_SQUAD, CAPTURE_ADJACENT. Приёмка реальной посадки/перевозки, целевого сектора и прекращения конфликтующих supervisor-команд.
4. Авиация/снабжение/ПВО: распределение ролей, безопасный резерв, ограничения РЛС, отдельное сопровождение Ту-95. Модель не выдаёт огневых разрешений вне физической политики.
5. Точечное управление: сначала наблюдение/укрытие/посадка, затем подтверждённая цель и перестановка техники. Проверить сохранение исходной группы, ручное управление, HC/Zeus/UAV, передачу locality и корректное освобождение прав.
6. Стратегия и вторые backend: измерить p50/p95 от события до STARTED, проценты EXPIRED/REJECTED, повторные запросы, токены/мин и фактическое выполнение. Не путать HTTP success с результатом в Arma.

Использовать отдельный Eden Test мод и тестовые сценарии. Новый адаптер сначала выключен по умолчанию; выключение LLM оставляет работоспособными навыки, снабжение, ПВО и автономную авиацию. Продуктовая настройка должна позволять выбрать уровни LLM и разрешить/запретить точечное вмешательство, сохраняя исключённые игроком отряды.

## Продолжение разработки

Начать с backend-независимого контракта и shadow-адаптера кампании. Прочитать actual source для campaignOrder/Buy/Ride/Lift/AirTask/AirDefense и bridge/protocol; сверить действующие guards перед добавлением. Не подключать новые управляющие вызовы до серверного lease/epoch-арбитра и проверки взаимодействия с существующими supervisor-циклами. Для каждого навыка сначала определить событие STARTED и наблюдаемый критерий результата. Промпт в соседнем документе — начальный проект; production формируется из версии реестра и актуальных возможностей игры.
